# Code review: benefit-be (001-case-lifecycle), re-review

**Verdict: PASS**: 0 blocking, 6 minor. Reviewed `wf.py delta` since the last review (branch `feature/001-case-lifecycle`, 58 uncommitted files, merges cleanly) and re-checked BE-1 to BE-5. The changed worker, API service, router and integration tests pass (49 passed), and `mypy --strict apps/api apps/worker` passes.

**Earlier findings**
- BE-1 (major): **fixed.** `record_case_change` and `determine_eligibility` go through `_until_done`, so when the retry policy runs out the workflow waits on a timer instead of failing. Two new workflow tests make 12 attempts fail (more than the 5 DEFAULT attempts), and the case still decides with `open=False` and seq `[1,2,3]`. Both tests would fail without the change.
- BE-2 (major): **fixed.** A cross-household reference now returns a coded 409 (`submission_reference_in_use`, field `submission_reference`) that doesn't reveal the other case. Service tests cover both the same-reference race (`RacingCaseRepository`) and the other-household path. The OpenAPI and the contract YAML are updated.
- BE-3, BE-4, BE-5: still open (below).

**New code, judged on its own**
- `_until_done` is deterministic: `workflow.sleep` is a durable timer, `retry_state` comes from history, and the success path issues the same commands as before. Problems are BE-6 and BE-7.
- `record_rejected_action` puts an `$setOnInsert` upsert keyed by `request_id` and the audit write in one `with_transaction`, and writes the audit entry only on insert. That makes it idempotent: a concurrent duplicate hits a write conflict, retries, then matches and writes no audit entry. The integration test checks one document and one audit entry after two calls. The router tests cover the decided-case path (with a retry giving one entry) and the running-workflow path (nothing written by the API).
