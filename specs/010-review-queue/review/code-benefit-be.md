# Code review: benefit-be (010-review-queue), round 4

Scope: the CR-BE-10 fix only (uncommitted, `feature/010-review-queue`): `ReviewLoop.alongside` in `apps/worker/workflows/review.py`, `ReviewHarnessWorkflow.run`/`_drive` in `review_harness.py`, and `test_FR_010_03_projection_rejected_holds_case_without_retry_loop`. Verdict: **PASS**, 0 blocking (0 critical, 0 major), 9 minor (7 carried over, 2 new).

- **CR-BE-10: resolved.** `alongside` awaits both tasks in the run coroutine. If the loop finishes first, `loop.result()` re-raises `ProjectionRejected` there, which fails the workflow task (a `RuntimeError` subclass, and no `workflow_failure_exception_types` is set). On retry, replay reaches the same rejection, so the case is held deterministically. The test now asserts a `WorkflowTaskFailed` event with "close_review_task was rejected", which a silently dead loop would not produce. The caller's mutation check confirms the test would fail without the fix. `test_review_failures.py` and `test_review_replay.py` pass (10 tests).
- **Errors from main: propagate.** `work.result()` re-raises the host's own error, and `finally` cancels the loop. The loop is checked first, so if both finish in the same tick the hold wins. That is the right choice. A loop that returns without an error raises `RuntimeError` and also holds.
- **Workflow cancel: propagates.** The SDK cancels the primary (run) task. `CancelledError` surfaces at the `asyncio.wait` call, and `finally` cancels both children. Before this change, the loop task was never cancelled. See minor 9 for the caveat.
- **Determinism and sandbox:** `asyncio.create_task` runs on the workflow event loop, which is deterministic and in order. `asyncio` is passed through by the sandbox. The replay test against `review_v1.json` still passes, because the loop's first pass issues no commands, so the order of commands is unchanged. `asyncio.wait` is safe here only because the returned sets are never iterated. The SDK says to use `workflow.wait` instead (minor 8).
