# ai-immersion-metarepo

Central store for the AI-assisted development assets shared by the Benefit projects:

| Folder | Purpose |
|---|---|
| `docs/` | How the workflow works, with diagrams: start with [docs/workflow-architecture.md](docs/workflow-architecture.md) |
| `workflows/` | `feature.md` (the stages) and the automated workflows `benefit-feature/` and `lane-chain/` |
| `agents/` | Roles (architect, quality engineer, compliance reviewer) and code-review agents; see `agents/README.md` |
| `skills/` | Reusable skills / slash commands (one folder per skill, with `SKILL.md`) |
| `specs/` | Functional specs and technical plans per feature |
| `project-rules/` | Rule sets with IDs, mapped to repo paths in `project-rules/README.md` |
| `templates/` | Starter templates for specs, plans and rule files |

## Projects governed by this repo

- [benefit-fe](https://github.com/OWNER/benefit-fe) — React frontend
- [benefit-be](https://github.com/OWNER/benefit-be) — Python backend

Each project's `CLAUDE.md` points back to the rules in `project-rules/`.

## Linked repositories

Project repos are plain git clones under `repos/`, which is git-ignored (no submodules). Ask Claude Code or GitHub Copilot to "add <url>", or run directly:

```bash
skills/clone-repo/clone-repo.sh https://github.com/OWNER/benefit-fe.git
```

After cloning this metarepo, clone each project repo with `skills/clone-repo/clone-repo.sh <url>`, and keep them current with `skills/sync-repos/sync-repos.sh`.

To open a PR for changes in a cloned repo, use `git create-pr <repo-name> --branch feature/<NNN-feature> --message "<commit>"` (see the **create-pr** skill). It is a git alias kept in the committed `.gitconfig`; enable it once after cloning the metarepo:

```bash
git config --local include.path ../.gitconfig
```

`.claude/skills/`, `.github/skills/`, `.claude/agents/` and `.github/agents/` hold one link per skill and per agent, generated by `python3 scripts/sync-copilot.py` from `skills/`, `agents/*.agent.md` and the skills inside agent folders (for example `agents/architect/skills/`).

## Reviews

Three reviews run before any PR, in parallel. Each writes `specs/<NNN>/review/<name>.md` and `.json`:

| Review | Checks |
|---|---|
| `backend-reviewer` | bugs, async and MongoDB mistakes, Temporal in practice, security, tests, design in `benefit-be` |
| `frontend-reviewer` | state and data bugs, security, accessibility, tests, design and API-contract fit in `benefit-fe` |
| compliance review | the constitution, the rule sets mapped to each changed path, Accepted ADRs, the test plan, secrets and synthetic data |

Run them yourself with `/review-changes`. In the feature workflow they run automatically, once tests and builds pass. A repo passes when no review has a critical or major finding and the branch merges cleanly into `main`. Re-reviews read only what changed since the last round.

## Opening PRs

### Before you start (once)

```bash
gh auth login        # the GitHub CLI opens the PRs
```

### Open the PR: `/create-pr`

Once the review approves, type `/create-pr` or ask "create a PR". The agent:
1. Picks the branch name from the spec folder (`specs/003-user-login/` → `feature/003-user-login`), using the same name in both repos if the feature touches both.
2. Writes the commit message (Conventional Commits) and fills the PR description from [templates/github/pull_request_template.md](templates/github/pull_request_template.md), including the review results and test commands.
3. **Shows you the repo, branch, files and PR title, and waits for your OK.**
4. Runs `skills/create-pr/create-pr.sh` for each repo: branch from `origin/main`, commit, push to that repo's own GitHub remote, open a PR against `main`. Running it again on the same branch adds a commit to the existing PR.

If the API contract changed, the `benefit-be` PR is opened first, then the `benefit-fe` PR that regenerates the client, and the two link to each other. The script never pushes to `main`, force-pushes or skips git hooks.

To run it yourself:

```bash
skills/create-pr/create-pr.sh benefit-fe \
  --branch feature/003-user-login \
  --message "feat(login): add login page" \
  --title "feat(login): add login page" \
  --body-file pr-body.md          # optional; add --draft for a draft PR
```

### After the PR merges: `/sync-repos`

Type `/sync-repos` or ask "sync the repos". It brings each clean clone in `repos/` up to the latest `main`. Clones with a feature branch or uncommitted changes are reported and left alone.

## Automated feature workflow

Full explanation with architecture and pipeline diagrams: [docs/workflow-architecture.md](docs/workflow-architecture.md).

Write the spec (`/speckit-specify`), then build it end to end:

```bash
specify workflow run workflows/benefit-feature/workflow.yml -i feature=003            # or /feature-workflow in chat
specify workflow status <run-id>      ·      specify workflow resume <run-id> [-i <gate>_verdict=approve]
```

```
CHAIN     pick up spec → spec check ─(open questions?)→ [you]
          → ARCHITECT: plan, research, data model, contracts, ADRs, scope → checks ─(a decision that's yours?)→ [you]
          → TASKS + QUALITY ENGINEER: tasks by lane, test plan, QA tasks → checks → branches → contracts
PARALLEL  one chain per lane: implement (tests first) → lane unit tests → fix
CHAIN     QA tests (contract, integration, e2e, eval) → ownership check
VERIFY    ≤3 rounds: tests and builds in parallel → if green: code + compliance reviews in parallel → fix
CHAIN     traceability → draft PRs (pr_mode=draft) · [you] first (pr_mode=ask) · stop (none) → GitHub Actions
```

- **People** are asked only for open spec questions, decisions that are theirs, and before pushing with `pr_mode=ask`. By default your review happens on the draft PRs in GitHub.
- **Verification** is by script after every stage (`workflows/benefit-feature/scripts/wf.py`): spec, plan, decisions, scope, task tags, test plan coverage, file ownership, tests and builds, reviews, requirement traceability and CI. A failed check stops the run; fix it and `resume`.
- **Tokens:** three AI sessions plan the whole feature (architect; tasks with quality engineering; contracts), reviews only run on green builds, re-reviews read only the change, and every role writes results to files and replies in a few lines (`agents/README.md`).
- **Before the first run:** `gh auth login`; both repos cloned in `repos/`; and allow the scripts, `git`, `make`, `uv`, `pnpm`, `python3` and `gh` in your Claude Code settings (AI steps run unattended, up to four at once). The engine runs Claude Code; Copilot users follow [workflows/feature.md](workflows/feature.md) by hand.

## Claude Code and GitHub Copilot

Both tools share `skills/`, `agents/` and `project-rules/`. Copilot's own files (`.github/copilot-instructions.md` and the slash commands in `.github/prompts/`) are generated from `CLAUDE.md` and the skills:

```bash
python3 scripts/sync-copilot.py          # regenerate
python3 scripts/sync-copilot.py --check  # fail if out of date
```
